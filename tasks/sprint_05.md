## Status Notes

- S5-003 (complete): added the shared scout order validator in `packages/game/src/movement/scout-order-validation.ts`, the server-side order-creation mutation in `apps/web/src/lib/kingdom/scout-orders.ts`, the bounded scout target read model in `apps/web/src/lib/kingdom/scout-target-options.ts`, and the `/army` `ScoutOrderPanel` UI. A dispatch reserves `SCOUTS` from the `SCOUTS`/`GARRISON` `UnitStack` with a conditional atomic decrement and writes a `MovementOrder` row with `orderType: "SCOUT"` and `status: "IN_TRANSIT"`.
- S5-003 deliberately did NOT ship arrival resolution. No `Report` row is written at dispatch, nothing transitions the order past `IN_TRANSIT`, no return leg is created, and the tick worker still has no movement processing. That gap is now closed by S5-004 below.
- S5-004 (complete): added the shared band approximation in `packages/game/src/movement/scout-report.ts` (`approximateScoutObservation`, `buildScoutReportBody`, `SCOUT_BAND_LABELS`), the tick-worker movement arrival pass in `workers/tick-worker/src/movement-arrival.ts` (`processMovementArrivals`), the null-safe display parser in `apps/web/src/lib/kingdom/scout-report-display.ts`, and scout report rendering in `ReportsPanel` plus the `/army` and `/reports` copy.
- The tick worker now resolves movement arrivals inside the existing `prisma.$transaction` (30s timeout), at the start of the transaction before the per-kingdom loop, as TWO ORDERED PASSES: PASS 1 completes `RETURN` legs (upsert-increment the source garrison `UnitStack`, then `COMPLETED` with `returnAt`), THEN PASS 2 handles arriving `SCOUT` orders (write the `SCOUT` `Report` on the SOURCE kingdom, set the outbound order `RESOLVED` with `resolvedAt`, create the `RETURN` leg). The ordering is load-bearing so a unit coming home this tick is back in the garrison before the economy loop reads Food consumption and army totals.
- `resolvedAt`, `returnAt`, and `parentOrderId` are now actually written. The return leg REUSES the outbound order's own `travelTicks` rather than recomputing it, so the trip home is symmetric, and its `arrivalAt` is `getMovementReturnAt(now, travelTicks)`. `parentOrderId` is UNIQUE and the worker checks for an existing leg first, so re-runs are no-ops.
- The report is APPROXIMATE BY DESIGN and deliberately leaks NO exact enemy value: no exact unit counts, no exact Food, no exact land, no building levels. Only coarse bands (army `SMALL/MEDIUM/LARGE` at 50/200 units, food `LOW/MEDIUM/HIGH` at 1,000/5,000, wall `NONE/LOW/MEDIUM/HIGH` at levels 1/3, defence `WEAK/NORMAL/STRONG` from `wallLevel*3 + watchtowerLevel*2 + floor(defensiveLandM2/2000)` cut at 6/16) plus a land band rounded to the nearest 10,000 m2 with a 10,000 m2 floor. `approximateScoutObservation` is deterministic (no `Math.random`, no clock reads) so a retried tick cannot change a report.
- Every band threshold is a v0.1 BALANCE PLACEHOLDER, not a locked decision, and needs retuning against playtest data — the same status as `MOVEMENT_BASE_METERS_PER_TICK` from S5-002.
- Failure isolation is per order: each order is processed in its own `try`/`catch` and failures become `warnings` on `MovementArrivalSummary`, so one poisoned row cannot abort the tick or lose other arrivals. A failed report write still resolves the order and still creates the return leg, and a vanished target kingdom still returns the scouts, so no arrival is ever left stuck `IN_TRANSIT` past its `arrivalAt` and no scouts are stranded off-map. Malformed `unitsJson` entries (zero, negative, fractional, `NaN`, unknown unit type) are dropped and counted rather than written through, which is what guarantees a bad manifest can never drive a garrison below zero.
- "Scout reports are approximate" is ticked. The sprint-doc criteria `Scout report is created on arrival` and `Scout report shows approximate information` are also now satisfiable and are ticked there. "Protected kingdoms cannot be attacked or scouted" stays unchecked because the combined criterion also requires attacks, which do not exist.
- Reports appear on the NEXT TICK after arrival, not instantly, and the `/army` and `/reports` copy now says so plainly.
- **S5-005 ships DISPATCH ONLY. A dispatched attack currently HAS NO EFFECT.** The order is written `IN_TRANSIT` and the units are reserved, but nothing happens at the target: no battle is fought, no casualties are dealt, no land is taken, and no battle report is written. The tick worker still has no `ATTACK` arrival branch, and those behaviours belong to S5-006 through S5-010. Treat the attack panel as staging an army on the road, and do not read any surface as implying that an attack resolves.
- S5-005 (complete): added the SHARED target-eligibility module `packages/game/src/movement/target-eligibility.ts` (`validateMovementTarget`, plus the `isKingdomUnderBeginnerProtection` implementation that moved here from the scout validator), the shared attack validator `packages/game/src/movement/attack-order-validation.ts` (`validateAttackOrder`), the dispatch mutation `apps/web/src/lib/kingdom/attack-orders.ts` (`createAttackOrderForUser`), the bounded attack read model `apps/web/src/lib/kingdom/attack-target-options.ts` (`getAttackTargetOptionsForUser`, `getAttackArmyStacksForUser`), and the `/army` `AttackOrderPanel` UI. A dispatch writes a `MovementOrder` row with `orderType: "ATTACK"` and `status: "IN_TRANSIT"`.
- The four target rules that S5-003 inlined in the scout validator (`INVALID_TARGET`, `SELF_TARGET`, `TARGET_NOT_FOUND`, `TARGET_PROTECTED`) now live ONCE in `target-eligibility.ts` and both the scout and attack validators delegate to them. The reason is a real drift hazard rather than tidiness: the protection boundary is `protectionEndsAt > now` STRICTLY, so a timestamp exactly equal to `now` has already expired. Two independent copies of that comparison would eventually disagree, and a drift there is a gameplay AND security bug — one kingdom becomes attackable while the other still refuses. All 25 pre-existing scout tests pass UNCHANGED, which is what evidences that the refactor was behaviour-preserving.
- An attack army is MIXED and may carry several unit types, unlike the scouts-only scout manifest. The validator rejects an UNRECOGNIZED unit type outright (`INVALID_UNIT_TYPE`) rather than dropping it, because silently dropping a bad entry would shrink the attacker's declared army without telling anyone. Duplicate manifest entries for the same unit type are AGGREGATED against supply rather than each checked independently: 60 + 60 `INFANTRY` against a garrison of 100 must fail, not pass two half-fits.
- Multi-unit reservation is ALL-OR-NOTHING. Every unit type is reserved with its own conditional atomic `updateMany` guarded by `quantity: { gte }`, and if any single one matches zero rows the transaction throws and rolls back entirely, so an attacker never loses some units and gains no order. A read-then-write guard would let two concurrent attacks both pass validation and both spend the same units. The rollback is tested for a LATER unit type failing and for the FIRST one failing.
- The manifest is re-validated and re-normalized against database state inside the `Serializable` transaction, and `unitsJson` stores the NORMALIZED manifest from the validator, never the raw client input. Travel speed uses the existing "an order moves at the pace of its slowest unit" rule, so a mixed army containing `SIEGE` is far slower than cavalry for the same distance.
- Beginner protection gates the TARGET only; a protected SOURCE kingdom may still attack an unprotected target. That matches the S5-003 locked-decision reading that a protected kingdom keeps build/train/buy land/prepare, and preparation includes sending an army out. Both halves are pinned by tests.
- The attack read model runs the SAME validator as the mutation, so the UI can never offer a target the mutation rejects; when the caller has no army at all, every target is marked un-targetable with `INSUFFICIENT_UNITS` rather than a misleading `INVALID_ARMY`.
- DELIBERATELY ABSENT: no alliance check (Sprint 6 has no `Alliance` schema, so "alliance members cannot attack each other" still CANNOT be enforced — this remains a live locked-rule gap that S5-005 does not close), no minimum or maximum army-size balance rule (deferred, the same status as `SCOUT_ORDER_MAX_SCOUTS`), no battle resolution (S5-006), no defender bonuses (S5-007), no siege (S5-008), no war land capture (S5-009), and no battle report (S5-010).
- `Protected kingdoms cannot be attacked or scouted` is now ticked because BOTH halves are genuinely enforced and pinned by tests: the scout half since S5-003 (`beginner-protected targets cannot be scouted`) and the attack half since S5-005 (`beginner-protected targets cannot be attacked` in the mutation, plus the read-model test asserting a protected target is listed but un-attackable). Everything about battles, defender bonuses, siege, alliances, war land capture, and battle reports stays unchecked.
